Table 1: Report Incident via Mobile App
Use Case 1: Report Incident
Use Case Goal:
To allow field reporters to submit geo-tagged incident reports with evidence (photos) and description for emergency response dispatch.
Scenario:
Scenario 1: Successful incident submission with location and evidence.
Actor:
Field Reporter (Mobile App User)
Pre-condition:
The user is logged in with valid Reporter credentials, has location permissions enabled, and has internet connectivity.
Main Flow:
Step 1:Reporter opens the mobile app and taps "Report New Incident".
Step 2:System requests permission to access device location and camera.
Step 3:Reporter captures up to 5 photos as evidence of the incident.
Step 4:System automatically fetches GPS coordinates and reverse geocodes to barangay and city.
Step 5:Reporter selects incident type (Fire, Medical, Accident, Crime, Infrastructure, Other).
Step 6:Reporter sets severity level (LOW, MEDIUM, HIGH, CRITICAL) based on situation.
Step 7:Reporter enters detailed description and personal contact information (name, phone).
Step 8:Reporter reviews all information and taps "Submit Incident".
Step 9:System validates all required fields and uploads incident with photos to Cloudinary.
Step 10:System creates incident with status REPORTED and broadcasts to Admin for verification (response units cannot see yet).
Step 11:System displays success confirmation screen with incident reference code and "Awaiting Verification" message.
User Action:
Reporter fills incident form with photos, location, type, severity, description, and personal information, then submits for verification.
System Response:
System validates all fields, uploads evidence to Cloudinary, creates incident with REPORTED status (pending admin verification), broadcasts notification to Admin for verification queue (not visible to response units yet), creates audit log entry, and returns reference code to reporter.
Table 2: Manage Incident Queue
Use Case 2: View Assigned Incidents
Use Case Goal:
To allow response units to view their assigned incidents on an interactive map with real-time updates and filtering capabilities.
Scenario:
Scenario 1: Response unit views incident queue and accepts assignment.
Actor:
Response Unit Officer (Web Dashboard User)
Pre-condition:
The user is logged in as Response Unit officer, incident has been verified and assigned to their unit by admin (status: RESPONDING), and they have access to Response Dashboard.
Main Flow:
Step 1:Officer logs into system and navigates to Response Unit Dashboard.
Step 2:System displays interactive map with all assigned incidents marked as colored pins (status: RESPONDING, ON_SCENE, RESOLVED).
Step 3:Officer receives real-time Socket.io notification when new incident is assigned by admin.
Step 4:Officer clicks on incident marker to view incident details (type, severity, location, reporter info, photos, reporter contact).
Step 5:Officer reviews incident severity, location, and evidence photos in modal.
Step 6:Officer clicks "Proceed to Scene" button to begin response.
Step 7:System updates incident status from RESPONDING to ON_SCENE.
Step 8:System displays GPS route navigation to incident location.
Step 9:Officer uses map for navigation and can contact reporter if needed via provided phone number.
User Action:
Officer views dashboard interactive map, selects an assigned incident, reviews all details and photos, and confirms "Proceed to Scene" to begin response.
System Response:
System displays interactive map with only assigned verified incidents (RESPONDING/ON_SCENE/RESOLVED), broadcasts assignment notification via Socket.io when admin verifies, shows comprehensive incident details in modal (including reporter contact), updates status to ON_SCENE upon confirmation, displays navigation route with distance/ETA, and logs status change in audit trail.
Table 3: Verify Incident Reports
Use Case 3: Verify and Dispatch Incidents
Use Case Goal:
To allow admin to verify submitted incidents, review evidence, and dispatch to appropriate response units based on incident type and severity.
Scenario:
Scenario 1: Admin verifies incident with valid evidence, approves dispatch, and assigns response units.
Actor:
System Administrator (Incident Verification Queue Page)
Pre-condition:
The user is logged in as Admin, incident is in REPORTED status (awaiting verification), and incident has photos and description.
Main Flow:
Step 1:Admin opens Incident Verification Queue page from Admin Dashboard.
Step 2:System displays list of incidents with status REPORTED (pending verification) with reporter info and submission time.
Step 3:Admin clicks on incident to view full verification modal.
Step 4:System displays modal with: reporter info (name, phone), incident code, description, and photo gallery.
Step 5:Admin examines all photos as evidence to validate incident credibility.
Step 6:Admin reviews incident type and severity classification for accuracy.
Step 7:Admin can edit incident type/severity if needed before approval.
Step 8:Admin can optionally add verification notes about the incident.
Step 9:Admin clicks "Approve & Dispatch" button.
Step 10:System executes smart assignment algorithm: matches incident type to unit type (Fire→FIRE, Medical/Accident→DRRMO, Crime→POLICE, Infrastructure→DRRMO).
Step 11:System assigns units based on severity: CRITICAL=5 units, HIGH=3 units, MEDIUM=2 units, LOW=1 unit.
Step 12:System uses geographic prioritization via PostGIS to find nearest available units in same barangay/city.
Step 13:System updates incident status from REPORTED to RESPONDING and creates assignment records.
Step 14:System broadcasts real-time dispatch notification to assigned response units via Socket.io.
Step 15:System creates audit log entry recording verification approval and assigned units.
Step 16:Admin sees confirmation message and incident is removed from verification queue.
User Action:
Admin opens verification queue, selects incident, reviews reporter info and photos, optionally edits type/severity and adds notes, and clicks "Approve & Dispatch" to trigger automatic unit assignment.
System Response:
System displays verification queue with REPORTED incidents and photo gallery in modal, allows editing type/severity/notes, executes smart assignment algorithm on approval (matches incident type→unit type, calculates units by severity), uses PostGIS for geographic prioritization, creates assignment records, updates status to RESPONDING, broadcasts dispatch notifications to assigned units via Socket.io, stores direction coordinates for navigation, and creates immutable audit log entries.
Table 4: Submit Post-Incident Report
Use Case 4: Submit Post-Incident Report
Use Case Goal:
To allow response units to submit after-action reports following incident completion with casualty data, damages, and actions taken.
Scenario:
Scenario 1: Successful post-incident report submission by response unit after incident is resolved.
Actor:
Response Unit Field Officer (Mobile or Web Dashboard)
Pre-condition:
The user is logged in as Response Unit officer, incident status has been changed to RESOLVED, and officer is authorized for the response unit.
Main Flow:
Step 1:Officer marks incident status as "RESOLVED" after completing response operations.
Step 2:Officer navigates to "Incident Details" page for completed incident.
Step 3:System displays incident summary and "Submit Post-Report" button (only available after RESOLVED status).
Step 4:Officer clicks button to open post-incident report form.
Step 5:Officer enters casualty data (deceased, injured, affected families) based on actual field assessment.
Step 6:Officer documents damages (property loss amount, critical infrastructure affected, displacement count).
Step 7:Officer describes detailed actions taken (rescue operations, medical aid provided, evacuation details, equipment used).
Step 8:Officer can upload additional evidence photos from field operations to Cloudinary.
Step 9:Officer reviews completed report for accuracy and completeness.
Step 10:Officer clicks "Submit Post-Report" button.
Step 11:System validates all required fields are completed.
Step 12:System saves post-incident report with status PENDING_REVIEW and notifies Admin.
Step 13:System creates audit log entry recording report submission.
User Action:
Officer opens incident details after marking RESOLVED, fills post-incident form with casualty data, damages, and actions taken, uploads evidence photos, and submits report for admin review.
System Response:
System displays post-incident form with all required fields only after RESOLVED status, validates data completeness and numeric formats, uploads evidence photos to Cloudinary, stores report with PENDING_REVIEW status, notifies Admin dashboard, creates audit log entry with timestamp, and confirms success to officer.
Table 5: Review Post-Incident Reports

System Administrator (Admin Dashboard)

Table 6: View Incident Analytics and Trends
Use Case 6: Analyze Incident Trends and Forecasts
Use Case Goal:
To allow admin to view incident statistics, historical trends, and AI-powered forecasts for strategic resource planning and emergency preparedness.
Scenario:
Scenario 1: Admin views analytics dashboard and 7-day incident forecast.
Actor:
System Administrator (Admin Analytics Page)
Pre-condition:
The user is logged in as Admin, historical incident data exists (minimum 30 days), and ML service is active.
Main Flow:
Step 1:Admin navigates to "Analytics" page from Admin Dashboard.
Step 2:System displays key statistics: total incidents, average response time, incidents by type (pie chart).
Step 3:System displays historical incident trend chart (last 30 days line graph).
Step 4:System calls ML microservice to generate 7-day forecast using SARIMA algorithm.
Step 5:System displays forecast chart with projected incident counts and confidence intervals.
Step 6:Admin can select date range to refine analytics view.
Step 7:Admin can filter by incident type to see type-specific trends.
Step 8:System displays heatmap showing incident density by barangay/location.
Step 9:Admin can export analytics report as PDF or Excel.
User Action:
Admin opens Analytics page, reviews historical trends and AI forecasts, applies filters by date and incident type, and exports reports for planning.
System Response:
System queries incident database to calculate statistics and trends, calls ML microservice (SARIMA/Prophet algorithms) to generate 7-day forecast, displays interactive charts and heatmaps, allows filtering by date range and incident type, and provides export functionality for PDF/Excel reports.

Table 8: Access and Filter Audit Logs
Use Case 8: Review System Audit Logs
Use Case Goal:
To allow admin to access immutable audit logs for compliance, security monitoring, and accountability of all system actions.
Scenario:
Scenario 1: Admin reviews audit logs to verify system compliance and user actions.
Actor:
System Administrator (Audit Logs Page)
Pre-condition:
The user is logged in as Admin, audit logs exist in database, and admin has audit access permissions.
Main Flow:
Step 1:Admin navigates to "Audit Logs" page from Admin Dashboard.
Step 2:System displays comprehensive list of all system actions with color-coded action badges.
Step 3:Admin can filter logs by action type (CREATE, UPDATE, DELETE, LOGIN) using dropdown.
Step 4:Admin can filter by user to view specific user's actions.
Step 5:Admin can filter by resource type (Incident, Report, LGU, User, etc.).
Step 6:Admin can filter by date range to search historical records.
Step 7:Admin can export audit logs as CSV for external compliance audits.
Step 8:Logs are displayed with columns: timestamp, action, user, resource_type, resource_id, details.
Step 9:Admin cannot delete, edit, or modify any audit log entries (immutable).
User Action:
Admin opens Audit Logs, applies filters by action/user/resource/date, reviews entries, and optionally exports as CSV.
System Response:
System displays chronological audit log entries with color-coded action badges, allows filtering by action type/user/resource/date range, disables all delete/edit operations on logs (immutable), supports CSV export for compliance audits, and displays comprehensive details including timestamp, user identity, and action specifics.
Table 9: Send Broadcast Notifications
Use Case 9: Send Emergency Broadcast
Use Case Goal:
To allow admin to send priority broadcast messages to all response units for emergency alerts and critical announcements.
Scenario:
Scenario 1: Successful emergency broadcast to all assigned response units.
Actor:
System Administrator (Broadcasts Page)
Pre-condition:
The user is logged in as Admin and response units are registered in system with active Socket.io connections.
Main Flow:
Step 1:Admin navigates to "Broadcasts" page from Admin Dashboard.
Step 2:Admin clicks "Create New Broadcast" button.
Step 3:System displays broadcast creation form with fields: title, message, priority, channel.
Step 4:Admin enters broadcast title and detailed message content.
Step 5:Admin selects priority level (LOW, MEDIUM, HIGH, CRITICAL).
Step 6:Admin selects delivery channel (In-App, SMS, Email, All).
Step 7:Admin can select target recipients or send to all active response units.
Step 8:Admin reviews broadcast preview and confirms submission.
Step 9:System immediately sends broadcast via Socket.io to connected units.
Step 10:System creates audit log entry and broadcasts notification history record.
User Action:
Admin creates broadcast with title, message, priority level, selects channel and recipients, and confirms to send immediately.
System Response:
System displays broadcast form with all required fields, validates message content, immediately transmits via Socket.io to all selected/active response units, creates notification history record with PENDING status, sends SMS/Email based on selected channels, records action in audit logs, and updates delivery status as confirmed.
Table 10: Track Notification Delivery
Use Case 10: View Notification History and Delivery Status
Use Case Goal:
To allow admin to track all sent notifications, monitor delivery status progression, and verify response unit message receipt.
Scenario:
Scenario 1: Admin views notification delivery timeline and status updates.
Actor:
System Administrator (Notification History Page)
Pre-condition:
The user is logged in as Admin and notifications have been sent to response units.
Main Flow:
Step 1:Admin navigates to "Notification History" page from Admin Dashboard.
Step 2:System displays list of all sent notifications with type, recipient count, and delivery status badges.
Step 3:Admin can filter notifications by type (Incident, Broadcast, Alert).
Step 4:Admin can filter by delivery status (PENDING, SENT, DELIVERED, READ, FAILED).
Step 5:Admin can filter by date range to find specific notifications.
Step 6:Admin clicks on notification to view detailed timeline modal.
Step 7:Modal displays delivery progression for each recipient: sent time, delivered time, read time.
Step 8:Admin can see which response units have not yet read the notification.
Step 9:System displays status icons and timestamps in chronological order.
User Action:
Admin opens Notification History, applies filters, selects notification to view delivery timeline, and reviews recipient read status.
System Response:
System displays all sent notifications with delivery status badges, allows filtering by type/status/date range, displays detailed timeline modal showing delivery progression (PENDING→SENT→DELIVERED→READ), displays delivery timestamps and recipient identities, and highlights unread messages for follow-up.
