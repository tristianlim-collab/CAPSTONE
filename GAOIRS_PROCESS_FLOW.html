🔄 Detailed Step-by-Step Process

Phase 1: Incident Creation & Reporting

1 Reporter Initiates Incident Report
Field reporter opens mobile app (or calls dispatch) and starts creating an incident report.
UI Flow:
Mobile App → Home Screen → "Report Incident" Button → Form Screen
Actor: Field Reporter (Citizen/Volunteer)
Status: CREATING
2 Capture Evidence (Photos)
Reporter takes up to 5 photos from the scene using device camera. Photos are stored locally first (offline support).
Data Created:
Evidence records with file_path (Cloudinary URL after upload)
file_type: "image/jpeg", "image/png" etc
Actor: Field Reporter
Storage: Cloudinary (remote), Local queue (offline)
3 Auto-Detect Geolocation
System uses GPS to detect reporter's current location. Coordinates (latitude, longitude) are captured. Reverse geocoding identifies barangay & municipality.
Data Captured:
latitude: Float (e.g., 14.2905°)
longitude: Float (e.g., 120.9789°)
barangay_id: UUID (via PostGIS query)
map_pin_address: String (e.g., "Anabu II-A, Imus, Cavite")
Actor: Mobile App (location service)
Data Source: Device GPS + Reverse geocoding API
4 Select Incident Type
Reporter selects incident type from color-coded list fetched from backend. Each type has a name, icon, and associated unit type.
Available Types:
🔴 Fire (FIRE unit)
🟢 Medical/Health Emergency (MEDICAL/DRRMO unit)
🔵 Accident (DRRMO unit)
🟡 Crime/Public Disturbance (POLICE unit)
⚪ Other/Infrastructure (BARANGAY/DRRMO unit)
Actor: Field Reporter
5 Describe Incident & Select Severity
Reporter provides text description of what happened and selects severity level (LOW, HIGH, CRITICAL). System assigns priority based on severity.
Data:
description: String (max 500 chars)
severity: Enum (LOW | HIGH | CRITICAL)
priority: Enum (AUTO-CALCULATED: CRITICAL→HIGH, HIGH→MEDIUM, LOW→LOW)
Actor: Field Reporter
6 Enter Personal Information
Reporter provides name and contact number (optional override if different from account). This allows anonymous reporting and field reporters to report on behalf of others.
Data:
reporter_name: String (optional, can override user account name)
reporter_phone: String (optional, can override account phone)
Actor: Field Reporter
7 Submit Incident Report
Reporter taps "Submit" button. System creates incident record and uploads evidence photos. Offline queue auto-syncs when online.
Records Created:
1. Incident record with incident_code (auto-generated: INC-YYYYMMDD-XXXXX)
2. Evidence records for each photo
3. First IncidentStatusLog: REPORTED status
status: "REPORTED"
reported_at: NOW()
Status: REPORTED
Actor: Field Reporter → Mobile App → Backend API
Endpoint: POST /api/incidents

Phase 2: Verification & Smart Dispatch

8 System Processes Incident (Automatic)
Backend automatically processes the newly created incident. System verifies data integrity, validates location within LGU boundaries.
Validations:
✓ Incident code uniqueness
✓ Location coordinates valid
✓ Incident type exists
✓ Reporter exists and is active
Status: VERIFIED
Actor: Backend Service (Automatic trigger)
Trigger: Socket.io event: "incident_created"
🎯 Smart Unit Assignment Decision Logic:

IF incident_type = "Fire"
  → ASSIGN TO: FIRE units in same barangay (sorted by distance & availability)

ELSE IF incident_type = "Medical/Accident"
  → ASSIGN TO: MEDICAL or DRRMO units (sorted by distance & availability)

ELSE IF incident_type = "Crime"
  → ASSIGN TO: POLICE units (sorted by distance & availability)

ELSE IF incident_type = "Infrastructure/Other"
  → ASSIGN TO: DRRMO or BARANGAY units

FOR EACH: Severity to Capacity Limit
CRITICAL: Assign up to 5 units
HIGH: Assign up to 3 units
LOW: Assign 1 unit
9 Automatic Unit Assignment
System automatically selects appropriate response units based on incident type, severity, and unit availability/proximity. Uses PostGIS to find geographically closest available units.
Records Created:
IncidentAssignment records (1-5 depending on severity)
assignment_id: UUID
status: "PENDING"
assigned_at: NOW()
assigned_by: Admin user (or system if auto-assign)
Status: RESPONDING (assignment created)
Actor: Backend Service (Automatic)
Logic: responseUnitController.autoAssignUnits()
10 Generate & Send Notifications
System sends multi-channel alerts to assigned units and admin dashboard. Notifications triggered via Socket.io for real-time delivery.
Notification Records Created (One per Unit + Admin):
notification_id: UUID
incident_id: UUID
unit_id: UUID (for unit notifications)
channel: SMS | EMAIL | PUSH | DASHBOARD
delivery_status: PENDING → SENT → DELIVERED
message_body: "New incident assigned: [INC-CODE] [TYPE] at [LOCATION]"
Delivery Channels:
📱 SMS: Twilio API (for feature phones)
📧 Email: Nodemailer
🔔 PUSH: Firebase Cloud Messaging (Android/iOS)
📊 DASHBOARD: WebSocket broadcast to admin panel
Status: NOTIFICATION SENT
Actor: Backend Service (socketService, notificationController)
Event: "incident_assigned" → All connected admins

Phase 3: Unit Response & Tracking

11 Unit Acknowledges Assignment
Response unit receives notification and confirms receipt by tapping "Accept" or "Reject". System records acknowledgment timestamp and updates assignment status.
Update IncidentAssignment:
status: "ACCEPTED" (or "REJECTED")
acknowledged_at: NOW()
Update IncidentStatusLog:
status: "VERIFIED" (if accepted)
Status: ACCEPTED
Actor: Response Unit (dash cam driver/commander)
12 Admin Views Real-Time Incident Map
Admin/dispatch coordinator monitors all active incidents and unit locations on a Leaflet-based interactive map. Can see incident markers, unit positions, and routes.
Dashboard Data (Real-Time via WebSocket):
incident_id, incident_code, type, location
unit_id, unit_name, unit_type, current_location
assignment_status (PENDING | ACCEPTED | ON_ROUTE | ON_SCENE | RESOLVED)
Incident colored by severity: RED=CRITICAL, YELLOW=HIGH, BLUE=LOW
Actor: Admin/Dispatcher
UI: React Admin Dashboard, Leaflet Map Component
13 Unit En Route to Incident
Response unit departs from station/location and begins navigating to incident scene. Mobile app receives turn-by-turn directions via embedded map.
Update IncidentAssignment:
status: "RESPONDING"
Update IncidentStatusLog:
status: "RESPONDING"
remarks: "Unit en route: [UNIT_NAME]"
Status: RESPONDING
Actor: Response Unit driver
14 Real-Time Location Updates
Unit's mobile app periodically (every 30 seconds) sends GPS location to backend. Admin dashboard updates unit positions in real-time. All stakeholders see progress.
Data Stream:
unit_id, latitude, longitude, timestamp
Update ResponseUnit record:
latitude: Float (current)
longitude: Float (current)
last_updated: NOW()
broadcast via Socket.io: "unit_location_updated"
Actor: Mobile App (background location service)
Frequency: Every 30 seconds
15 Unit Arrives at Scene
Unit arrives at incident location. Commander/driver confirms arrival by tapping "On Scene" button in mobile app.
Update IncidentAssignment:
status: "ON_SCENE"
arrived_at: NOW()
Update IncidentStatusLog:
status: "ON_SCENE"
Update Incident:
status: "ON_SCENE" (if first unit to arrive)
Status: ON_SCENE
Actor: Response Unit commander

Phase 4: On-Scene Response & Resolution

16 Unit Responds to Incident
Response unit conducts emergency response operations according to incident type and severity. Actions taken depend on specific incident (fire suppression, medical aid, law enforcement, etc).
Unit Captures Information:
- Actual conditions at scene
- Number of victims/affected persons
- Extent of damage
- Scene photos (additional evidence)
- Actions taken to resolve
Actor: Response Unit personnel
Duration: Variable (minutes to hours)
17 Unit Completes Response & Resolves
When incident is under control/resolved, unit commander marks incident as resolved through mobile app.
Update IncidentAssignment:
status: "RESOLVED"
resolved_at: NOW()
Update IncidentStatusLog:
status: "RESOLVED"
Update Incident:
status: "RESOLVED" (when all units mark resolved)
Status: RESOLVED
Actor: Response Unit commander
18 Unit Submits Post-Incident Report
Unit submits detailed after-action report through mobile app or web dashboard. Report includes response time, actions, casualties, damage estimates, photos, and remarks.
PostIncidentReport Created:
report_id: UUID
incident_id: UUID
submitted_by: User (response unit commander)
response_time_minutes: Int (calculated from arrived_at - reported_at)
actions_taken: String (detailed description)
casualties: Int (number of people affected)
damages_estimate: String (estimated cost)
photos: Array<String> (Cloudinary URLs)
remarks: String (additional notes)
status: "PENDING" (awaiting admin review)
submitted_at: NOW()
Status: PENDING REVIEW
Actor: Response Unit commander
UI: Mobile App → My Reports Screen

Phase 5: Admin Review & System Analytics

19 Admin Reviews Post-Incident Report
Admin/supervisor reviews submitted post-incident report to verify accuracy and compliance. Can add notes and approve/reject the report.
Admin Actions:
1. View all report details
2. Add admin_notes: String (optional comments)
3. Update status:
- "UNDER_REVIEW" (flag for deeper investigation)
- "APPROVED" (report accepted as accurate)
- "REJECTED" (report has errors, needs resubmission)
4. reviewed_by: User (who reviewed)
5. reviewed_at: NOW()
Status: APPROVED / REJECTED
Actor: Admin/Supervisor
UI: Admin Dashboard → Post-Incident Reports page
20 System Audits All Changes
Every action throughout the incident lifecycle is logged to SystemAuditLog for compliance and accountability. Immutable audit trail for regulatory oversight.
Audit Logs Created For:
✓ CREATE: New incident, new assignment, submission of post-report
✓ UPDATE: Status changes, admin notes added, location updates
✓ DELETE: (restricted to admins only)
✓ LOGIN: User authentication events

Audit Log Fields:
log_id, user_id, action, resource, resource_id
details: JSON string (old value → new value)
ip_address, created_at
Actor: Backend Service (Automatic on all changes)
Function: auditLog.track()
21 System Generates Analytics & Forecasts
ML service ingests incident data and generates 7-day trend forecasts using SARIMA and Prophet algorithms. Forecasting detects patterns and predicts peak incident times/areas.
Forecast Inputs:
- Historical incident data (past 30-90 days)
- Incident type, severity, location, time
- Seasonal patterns (weekday vs weekend)

Forecast Outputs:
- Next 7 days predicted incident counts
- Confidence intervals (upper/lower bounds)
- High-risk time windows
- Geographic hotspots

Algorithms:
SARIMA: Champion (RMSE 2.45) - captures weekly seasonality
Prophet: Backup (RMSE 2.78) - trend detection with holidays
Actor: ML Service (ml-service/ml-service.js)
Port: 5000
Trigger: Daily scheduled task or on-demand from admin
22 Admin Generates Custom Reports
Admin can generate PDF or Excel reports filtered by date range, incident type, barangay, severity. Reports include incident summaries, response times, trends, and statistics for LGU leadership.
Report Types:
📊 INCIDENT_SUMMARY: Count by type/severity
📍 AREA_REPORT: Incidents by barangay
⏱️ RESPONSE_TIME: Average response time metrics
📋 FULL_EXPORT: All incident details with full history

File Formats:
PDF (Cloudinary + custom formatting)
EXCEL (xlsx with charts)
CSV (for data import)

GeneratedReport Created:
report_id, generated_by, report_title, report_type
file_format, filters_applied (JSON), file_path, generated_at
Status: GENERATED
Actor: Admin
UI: Admin Dashboard → Reports/Analytics page
23 Incident Officially Closed
After post-incident report is approved and all data captured, incident lifecycle is complete. Status marked as CLOSED for archival.
Final Update to Incident:
status: "CLOSED"
Final IncidentStatusLog:
status: "CLOSED"
remarks: "Incident closed - Post-incident report approved"
Status: CLOSED
Actor: System (Auto-updated when post-report approved)

👥 Process Flow by User Role

📱 Field Reporter (Citizen/Volunteer)
  • Step 1-7: Create incident report with photos, location, type, severity, personal info
  • Step 23: View incident status & post-incident report status on "My Reports" screen
  • Access Levels: Only see own incident reports
🚨 Response Unit (FIRE, POLICE, MEDICAL, DRRMO, BARANGAY)
  • Step 11: Receive assignment notification, accept/reject
  • Step 13: Navigate to incident scene
  • Step 14: Continuous location sharing (background GPS every 30s)
  • Step 15: Confirm arrival at scene
  • Step 16-17: Conduct response operations, mark resolved when complete
  • Step 18: Submit post-incident report with details & photos
  • Access Levels: View own assignments, location, active incident data
👨‍⚖️ Admin/Dispatcher (LGU Official)
  • Step 8-10: Monitor system auto-assignment (can override if needed)
  • Step 12: View real-time incident map with all incidents & unit locations
  • Step 15-17: Track unit progress in real-time
  • Step 19: Review & approve/reject post-incident reports with audit notes
  • Step 20: Monitor audit logs for compliance
  • Step 21-22: View trend forecasts and generate custom reports
  • System Config: Manage LGU boundaries, unit assignments, alert settings
  • Access Levels: Full system access, can create custom reports, manage users

⚠️ Exception Handling & Error Scenarios

Offline Incident Queueing
Scenario: Field reporter has no internet connection

System Response:
• Incident stored in local SQLite queue
• Photos cached locally
• Auto-sync trigger when connection restored
• Successful message shown to reporter

Data Consistency: No incident_code assigned until server accepts
Unit Rejects Assignment
Scenario: Unit responds to assignment with "REJECTED"

System Response:
• IncidentAssignment status → REJECTED
• System auto-assigns to next available unit (same type)
• New notification sent to backup unit
• Admin notified of rejection

Failsafe: Always maintain backup unit queue per incident type
False Alarm Report
Scenario: Unit arrives and confirms incident was false

System Response:
• Incident status → FALSE_ALARM
• Add to audit log with remarks
• Post-incident report still required for tracking
• Unit availability updated quickly

Analytics Impact: False alarms tracked separately for analysis
Unauthorized Location Access
Scenario: Reporter provides coordinates outside LGU jurisdiction

System Response:
• PostGIS validation checks boundary
• Incident still created but flagged
• Admin receives alert for manual review
• May escalate to neighboring LGU if within their boundaries

Safeguard: Jurisdiction check at incident creation
Network Failure During Real-Time Tracking
Scenario: Unit loses connection while en route

System Response:
• Last known location retained on dashboard
• Unit can still navigate with offline maps
• Location updates resume when connection restored
• No loss of assignment data

Resilience: Graceful degradation with data buffering

🔒 Data Flow & Security Measures

Data Type Storage Location Security Measure Retention Policy
Incident Core Data PostgreSQL (Supabase) Encrypted at rest, JWT auth, Row-level security 7 years (regulatory requirement)
Evidence Photos Cloudinary CDN HTTPS, Access tokens, File size limits Lifetime (after approval)
Audit Logs PostgreSQL (immutable) Encrypted, No delete permission, Signed Permanent (compliance)
Passwords PostgreSQL (hashed) bcrypt (salt rounds: 10), Never logged Until password reset
FCM Tokens PostgreSQL Encrypted field, User-specific tokens Until logout/expiry
System Config PostgreSQL Encrypted values (AES-256), Admin-only access Until updated
